3.5. THERMAL POLICY
================================================================================
HyperCore does not implement thermal mitigation and does not touch the vendor
thermal stack. Frequency ceilings, throttling and battery safety are handled
exclusively by mi_thermald, FPSGO thermal and the GPU devfreq cooler shipped
with the ROM. The daemon keeps fpsgo_thrm_enable and Xiaomi sconfig at their
stock values in every profile and never writes to thermal policy nodes.
Gaming profiles hold the full hardware frequency ceilings; the vendor stack
remains the sole authority for stepping them down under heat.

3.6. Auto Game Detector & Foreground Process Scanner (src/gamelist.c)
- Reads configured package rules from `/data/adb/hypercore/gamelist.txt`.
- Lines are `package.name:PROFILE` (`GAMING`, `GAMING_MOBA`, `INTERACTIVE`,
  `SLEEP`); surrounding whitespace is ignored and profiles match
  case-insensitively, so hand edits with stray spaces still work.
- Evaluates foreground window focus using non-blocking window manager checks.
- If a foreground package matches a gamelist entry, the daemon transitions
  the system profile to `Gaming` or `Gaming MOBA`.
- When the application is dismissed or minimized, the daemon restores `Interactive`.
- First-boot auto-detect runs once and records
  `/data/adb/hypercore/.gamelist_autodetected`. An empty list after that
  means the user cleared it, so it is honoured — deleting `gamelist.txt`
  no longer resurrects it on restart. Scan again from the WebUI button,
  or remove the stamp file to force one more automatic pass.

3.7. UNIX Domain Socket IPC & Atomic Telemetry Storage (src/ipc.c)
- Listens on UNIX domain socket `/dev/hypercore.sock` (a compatibility symlink is
  kept at `<data_dir>/hypercore.sock` for older external scripts).
- Every client is authorised with `SO_PEERCRED` before the daemon reads from it.
  Accepted UIDs: 0 (root — all KernelSU/APatch/Magisk WebUI bridges and
  hypercore-bugreport spawn helpers as root) and 2000 (adb shell). Untrusted
  peers are closed immediately, so they cannot stall the tuning loop.
- Commands:
  * `GET_STATUS` / `STATUS`  : Returns JSON telemetry (profile, gpu load,
                              temps, uptime, DDR clock).
  * `SET_PROFILE:<name>`    : Manual override to AUTO, Sleep, Interactive,
                              Gaming, or MOBA. Unknown names are rejected
                              with an error instead of locking a profile.
  * `PURGE_RAM` / `CLEAR_CACHE` : Drop page cache and reclaim.
  * `PING`                  : Liveness check, replies `PONG`.
- Telemetry is also written atomically (tmp + rename) to `/dev/hypercore_status.json`
  and `<data_dir>/status.json`.
- Telemetry logs live at `/data/adb/hypercore/hypercore.log` (root-only), not
  under `/sdcard`.
- Function `update_status_json_file()` writes telemetry atomically using temporary
  files (`.tmp`) and `rename()`, preventing corrupt reads by the WebUI.

3.8. Storage I/O Queue & Memory / VM Optimization (src/io.c & src/memory.c)
- Storage I/O Optimization:
  Sets `read_ahead_kb=256`, `rq_affinity=2`, and `iostats=0` on UFS/eMMC devices
  to minimize CPU interrupt overhead during file operations.
- Virtual Memory Subsystem:
  Tunes `vm.swappiness=60`, `vm.dirty_ratio=15`, `vm.dirty_background_ratio=5`,
  `vm.vfs_cache_pressure=100`, and `vm.page-cluster=0` for optimal ZRAM utilization.

3.9. SHA-256 Payload Integrity Verification (src/integrity.c & src/sha256.c)
- Layer 1 (install): `customize.sh` runs `sha256sum -c checksums.txt` over the
  whole extracted payload *before* sourcing or executing any of it. The manifest
  covers the shipped scripts, `scripts/stock_baseline.sh`, and the
  `hypermoon_d` / `hypermoon.dex` / `hypercore-bugreport` binaries, plus
  `libhypercore.so` itself.
- Layer 2 (runtime): the daemon re-verifies the same set via a table compiled
  into the binary (`--verify-integrity`), minus `libhypercore.so` — a binary
  cannot contain its own hash, which is why layer 1 exists.

3.10. Single-Instance Lock (src/main.c)
- An advisory `flock(LOCK_EX | LOCK_NB)` on `<data_dir>/.hypercore_lock`,
  acquired after `daemon()` and released on exit. Two live daemons would fight
  over the same sysfs nodes and the loser's `restore_baseline_nodes()` would
  stomp the survivor's tuning, so a second instance refuses to start.

3.11. System Logging Infrastructure (src/log.c)
- Appends operational records, thermal events, and profile switches to
  `/data/adb/hypercore/hypercore.log` (root-only; deliberately not `/sdcard`).
- Features automated log rotation at 512 KB to keep file sizes lightweight.

4. HYPERMOON IN-GAME PERFORMANCE HUD SUBSYSTEM
================================================================================

4.1. Dual-Engine Architecture (hypermoon_d & HyperMoonOverlay.java)
HyperMoon is an integrated, low-latency on-screen performance monitor:
- Native C Collector (`hypermoon_d`): Gathers sub-millisecond FPS metrics
  from SurfaceFlinger / Mali GPU devfreq, CPU cluster loads, battery wattage,
  and network throughput, writing state to `/data/adb/hypercore/hud/stats.json`.
- Java DEX Overlay (`HyperMoonOverlay.java`): Executed via Android `app_process`,
  rendering hardware-accelerated text and pill overlays directly onto a native
  window overlay without requiring third-party APK installations.

4.2. Linux Kernel Inotify FileObserver Synchronization
- Utilizes Android`s `FileObserver` bound to `/data/adb/hypercore/hud/config.json`.
- When settings or sliders are adjusted in the WebUI, the Linux kernel triggers
  an immediate inotify event, applying layout, scaling, and theme adjustments
  in under 1 millisecond.

4.3. Instant Master Switch & Dynamic Geometry Engine
- Master ON/OFF toggle alters window visibility state in memory rather than
  killing or relaunching underlying processes, delivering zero switch delay.
- `calcHudDimensions()` dynamically recalculates line heights and bounding
  boxes to prevent metric clipping across screen rotations and aspect ratios.

4.4. Telemetry Metrics, Presets & Color Themes
- Metric Toggles: FPS, Frametime, CPU load/freq, CPU scaling governor, Mali GPU
  load/freq, Mali GPU governor, RAM, ZRAM swap, Battery wattage/temp, and Network.
- One-Tap Presets:
  * Minimal : Pure FPS counter for competitive esports.
  * Compact : Balanced essentials (FPS, CPU, GPU, Battery).
  * Detailed: Full telemetry stack including active scaling governors.
- Color Themes: Cyber Neon, AMOLED Dark, Matrix Green, Crimson Red, and Custom.

5. PERFORMANCE PROFILES SPECIFICATION & DYNAMICS
================================================================================

1. SLEEP (SCREEN OFF / IDLE):
   - Engaged automatically when the display turns off.
   - CPU scaling governor switched to powersave or conservative schedutil limits.
   - uclamp min reduced to 0; uclamp max clamped to suppress idle wakeups.
   - Mali GPU throttled to minimum hardware frequency (130 MHz / 260 MHz).

2. INTERACTIVE (DEFAULT / DAILY USE):
   - Active profile for daily navigation, browsing, and messaging.
   - GPU devfreq ceiling uncapped up to ~1003 MHz with responsive 65% upthreshold
     to eliminate UI frame drops.
   - Balanced uclamp min (10–20%) ensuring instant app launches.

3. GAMING (HIGH PERFORMANCE):
   - Triggered automatically when a standard 3D game launches.
   - CPU uclamp min raised to 30–50% to prevent frame drops.
   - cpufreq up_rate_limit accelerated to 1000 µs.
   - GPU floor elevated (390 MHz / 520 MHz) with `gx_game_mode=1`.

4. GAMING MOBA (ULTRA LOW-LATENCY):
   - Reserved for competitive titles (e.g., Mobile Legends, Wild Rift, PUBG).
   - Maximum safe CPU uclamp min (60–80%) for instant touch-to-frame rendering.
   - GPU floor elevated to 650 MHz / 800 MHz.
   - Helio DVFSRC QoS engaged for lowest memory bus interconnect latency.

6. MATERIAL DESIGN 3 WEBUI DASHBOARD (VUE 3 + PINIA SPA)
================================================================================

6.1. Telemetry Store Resilience & Zero-Flicker Architecture
- Pinia state store (`webui/src/stores/hyper.js`) handles asynchronous polling:
  * `pollCpuGpu()` : Runs every 1s for CPU/GPU loads and temperatures.
  * `pollRamBat()` : Runs every 2s for RAM and ZRAM telemetry.
- Multi-tier fallback prevents UI flicker: if socket queries experience brief
  contention, previously cached daemon PIDs and states are retained.

6.2. Single-File Artifact Distribution & View Modules
- Bundled into a single self-contained HTML document (`webroot/index.html`) using
  `vite-plugin-singlefile`, avoiding local web server dependency.

  * `GamesView.vue`   : Game profile assignment, auto-detector, and app picker.

7. INSTALLER LIFECYCLE & SECURITY VALIDATION
================================================================================

7.1. Module Installation Script (customize.sh)
- Kernel Compatibility Verification: Asserts Linux Kernel 5.10–6.12+ GKI.
- Hardware Validation: Verifies MediaTek MT6789 Family nodes (GED & Mali GPU).
- Daemon Upgrade Guard: Terminates running instances and purges old sockets
  before extracting new archives.
- User Data Preservation: Merges existing user `gamelist.txt` and hardware
  charging configurations from `/data/adb/hypercore/`.
- Automatic Game Detection: Scans installed non-system packages (`pm list packages -3`)
  and registers detected games automatically.
- Integrity Check: Verifies the entire extracted payload with
  `sha256sum -c checksums.txt` and then again via
  `libhypercore.so --verify-integrity` — both *before* any payload file is
  sourced or executed. Aborts the install on any mismatch.

7.2. Boot Service Launcher (service.sh)
- Awaits complete system initialization (`sys.boot_completed == 1`).
- Stops any previous daemon with SIGTERM, waits up to 10 s for it to restore
  baseline nodes, then escalates to SIGKILL.
- Launches `libhypercore.so` with automatic failure retry.
- Launches the HyperMoon daemon and overlay if the HUD is configured visible.
- Note: HyperCore does not touch other modules' scripts. Earlier revisions
  chmod'd any `service.d` / `post-fs-data.d` entry matching
  `thermal|tweak|encore|ktweak` to 0644, which silently disabled third-party
  modules, recorded no original file mode, and was never undone on uninstall.
  If you run a competing thermal module, disable one of them yourself.

7.3. Post-FS-Data Initialization (post-fs-data.sh) & Uninstaller (uninstall.sh)
- `post-fs-data.sh`: Creates the `/data/adb/hypercore` runtime state directory
  early so the daemon has a place for its pid, socket and configs.
- `uninstall.sh`: Completely terminates background processes, restores CPU
  governors and frequencies, resets Mali power policies, cleans up PATH symlinks,
  revokes the overlay permission grants, and moves user settings (including the
  gamelist and HUD layout) into a timestamped sidecar under
  `/data/adb/hypercore_removed/` before removing runtime state.

8. BUILD & DEPLOYMENT AUTOMATION (build.sh)
================================================================================
The repository build system (`build.sh`) manages the full build lifecycle:
1. Compiles WebUI into single-file `webroot/index.html` via Vite.
2. Regenerates `checksums.txt` and `src/include/embedded_checksums.h` every
   run, gated with `sha256sum -c` before packaging.
3. Compiles C sources with Clang using `-O3 -Wall -Werror` flags.
4. Packages clean release zip into `./out/`
   (`HyperCore-vX.Y.Z-bNNNN-Unified.zip`; override the destination with
   `HYPERCORE_OUT=...`).
5. When `--deploy` is specified, updates `/data/adb/modules/hypercore/` in-place
   and restarts active daemon instances.

Notes:
- A build never mutates source files; version strings in README and this
  document are updated in the release commit, not by the build script.
- The HUD dex overlay is optional: it is built when a Java toolchain
  (ecj/javac + dx/d8) is available and cleanly omitted otherwise — the
  manifest and zip adapt, and `service.sh` already guards the overlay launch.

9. DEVELOPMENT INVARIANTS & SYSTEM RULES
================================================================================
1. Zero Frequency Locking: Frequencies must remain dynamic under governor logic.
2. Target Hardware Scope: Strictly MediaTek MT6789 Family (Helio G99/G100/G200).
3. GKI Sysfs Fallback: Always use fallback arrays for Cgroup and kernel nodes.
4. Zero Storage Pollution: Build release ZIPs exclusively in `./out/` inside the
   repository (gitignored; override the destination with `HYPERCORE_OUT`).
5. Git Branch Workflow: Active development on `experimental`, fast-forward merged to `main`.
6. Language Standard: 100% natural, clean English across all code, UI, and documentation.
